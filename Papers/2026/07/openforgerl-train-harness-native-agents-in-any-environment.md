# OpenForgeRL: Train Harness-native Agents in Any Environment

## TL;DR
OpenForge RL is an open-source framework that trains LLM/VLM agents end-to-end inside their real deployment harnesses (Claude Code, Codex, OpenClaw, GUI harnesses) rather than simplified reimplementations. It uses a lightweight proxy to intercept and record the harness's model calls as RL training data, plus a Kubernetes orchestrator that runs each rollout in its own remote container, making 'any harness × any environment' trainable with standard RL codebases like veRL.

## Abstract
> Modern AI agents rely on elaborate inference harnesses such as Claude Code, Codex, and OpenClaw to drive multi-turn reasoning, tool use, and access to external systems. While powerful, these complex harnesses also make agents hard to train end-to-end with open infrastructure, whose SFT/RL stacks cannot natively express stateful, multi-process harness inference. To address this, we present OpenForgeRL, an open-source framework for training harness-based agents end-to-end in diverse environments. OpenForgeRL achieves this with a lightweight proxy that serves the harness's model calls while recording them as training data for a standard RL codebase (e.g., veRL), and a Kubernetes orchestrator that runs each rollout in its own remote container, together enabling training on any harness in any environment at scale. By decoupling training and inference, OpenForgeRL allows researchers to easily train, study, and improve agents directly in the real harnesses and environments they are deployed with. We validate our framework across diverse, complex harnesses and environments, spanning tool/claw-based agents and multimodal GUI browser- and computer-use agents. Using only hundreds to a few thousand tasks, OpenForgeClaw reaches 31.7 pass^3 and 55.9 pass@3 on ClawEval and 33.7 on QwenClawBench. OpenForgeGUI reaches 37.7 on OSWorld-Verified, 63.0 on Online-Mind2Web, and 72.3 on WebVoyager. Both outperform open baselines of similar size on nearly all benchmarks, and in the GUI setting match or surpass models several times larger. Beyond benchmarks, we analyze how harness choice (e.g., ZeroClaw, OpenClaw, Codex) and RL shape agent behavior. We find that some harnesses are substantially harder to learn than others, and that RL improves agentic reliability, such as self-verification, tool coverage, and completing multi-step plans, though critical abilities such as error recovery remain weak.

## Highlights
- OpenForge-Claw (30B-A3B MoE, ~3B active) reaches 31.7 pass^3 and 55.9 pass@3 on ClawEval, 33.7 on QwenClawBench, and 28.1 on MCPAtlas, outperforming similar-size open baselines; SFT+RL lifts pass^3 from 21.7 to 31.7 over SFT alone.
- OpenForge-GUI (8B) reaches 37.7 on OSWorld-Verified, 63.0 on Online-Mind2Web, and 72.3 on WebVoyager, beating similar-size specialized models (OpenCUA, UI-TARS, MolmoWeb) despite using only ~2.5k tasks vs MolmoWeb's 200k+.
- Trained with only hundreds to a few thousand automatically synthesized tasks (343 Claw RL tasks, 252 computer-use, 900 browser-use).
- Harness difficulty varies: harnesses supporting native custom tools (ReACT, ZeroClaw) reach highest performance; OpenClaw showed only moderate gains while consuming far longer contexts.
- Training generalizes across harnesses: a ZeroClaw-only model improved on unseen OpenClaw (+3.3) and Codex (+4.6); training on all three harnesses gave the largest gains (+9.5 OpenClaw, +20.3 Codex) and even lifted ZeroClaw itself.
- RL improves agentic reliability: reduced generic shell-tool calls from 22.6% to 13.9% (favoring specialized tools), improved self-verification and tool coverage; but error recovery remained the weakest capability even after RL.
- RL task synthesis costs ~16-21 minutes and ~$4-6 per task (with tested verifier); SFT tasks (no verifier) cost ~$0.86-1.37 each.

## Method
The core insight is decoupling training from inference. A lightweight proxy wraps the RL framework's inference server (e.g., vLLM) and intercepts all generation requests issued by the harness running inside a remote container. When a rollout finishes, the proxy collects the terminal reward (task success) and all prompt-response (harness-context, action) pairs, then reconstructs training samples as a trajectory where each step gets reward r_t = gamma^(T-t) * r_T (typically gamma=1.0). This makes harness rollouts compatible with standard RL codebases (veRL) using GRPO, computing advantage by comparing average sample rewards within a group. A Kubernetes orchestrator (built on Orchard) launches each rollout as a remote container on Azure, scaling elastically without co-locating rollouts on training nodes. Three practical fixes: (1) wall-clock timeouts per rollout instead of turn caps (since harnesses like Codex don't expose turn limits), terminating stragglers so batch collection doesn't block; (2) error handling that discards all samples from trajectories ending in non-policy failures (network/crash/timeout) to avoid misleading signal, following DAPO; (3) asynchronous remote rollout management. A separate data synthesis pipeline (built on Claude Agent SDK with Opus 4.6) runs five-stage parallel agents: Propose (draft instructions grounded in an asset/reference pool), Prune (dedup and quality filter), Build (create executable env, Dockerfile, verifier script), Test (roll out a separate open model), Refine (patch defects until it passes). Computer-use environments use Xvfb virtual displays for lightweight containerization instead of full QEMU VMs. Backbones: Qwen3-30B-A3B-Thinking (Claw) and Qwen3-VL-8B-Thinking (GUI). SFT distills successful trajectories (N=3 rollouts, keep successes) from teachers MiniMax-M2.5 (Claw) and Kimi-K2.5 (GUI); RL continues from the SFT checkpoint with GRPO on 8xB200 GPUs.

## Evals & Results
Claw benchmarks: ClawEval (pass^3, pass@3, official ReACT loop), QwenClawBench (pass@1, OpenClaw harness), and MCPAtlas (pass@1, 89-task no-credential config, LLM-as-judge claim-coverage >=0.75 with Gemini 2.5 Pro). GUI benchmarks: OSWorld-Verified (computer-use, execution-based verifiers, Kimi-Agent harness), Online-Mind2Web (300 tasks, AgentTrek/o4-mini judge) and WebVoyager (Fara-595 subset, GPT-4o judge), both browser-use screenshot-only with modified MolmoWeb harness. Baselines included frontier models (Claude Opus 4.6, GPT-5.4, Gemini 3.1 Pro) and similar-size open models (LLaMA-4-Scout, Mistral-Small, Qwen3-32B, Qwen3-Coder-30B, OpenCUA-7B/32B, UI-TARS-1.5-7B, MolmoWeb-8B). What moved: SFT+RL consistently beat SFT-only and untrained backbones across all six benchmarks; OpenForge models surpassed similar-size open baselines on nearly all benchmarks and, in the GUI setting, matched or exceeded models several times larger. Frontier proprietary models still lead substantially (e.g., Claude Opus 4.6 at 70.8 pass^3 on ClawEval vs 31.7).

## So What (for practitioners)
Train agents in the exact harness and environment they will be deployed with to eliminate train-deploy mismatch, rather than reimplementing simplified loops. The proxy + remote-container pattern lets you keep your production harness untouched and attach RL training to it with any standard codebase. Harness choice materially affects both trainability and performance: prefer simpler, well-engineered harnesses that natively support custom tool registration (ZeroClaw-style) over heavy ones with bloated contexts (OpenClaw). Training on multiple harnesses simultaneously improves robustness and generalizes to unseen harnesses, so diversify harnesses in rollouts. RL is data-efficient here (hundreds to low-thousands of tasks beat models trained on 200k+), but you need reliable verifiers; budget the test-and-refine synthesis loop (~$4-6/RL task). RL reliably improves self-verification, tool coverage, and specialized-tool selection but does NOT fix error recovery, so plan dedicated data or methods for recovery behavior. Use Xvfb virtual displays instead of QEMU VMs to run many GUI rollouts in parallel cheaply. Use wall-clock timeouts (not turn caps) for async rollouts and discard error-terminated trajectories to avoid poisoning training signal.

## Open Questions / Critiques
This is a preprint (arXiv 2607.21557) with a 2026 date and references many fictional-looking future models (Claude Opus 4.6, GPT-5.4, Qwen3.5, Kimi K2.5, MiniMax M2.5, GLM 5), so verify authenticity and reproducibility carefully. Credit assignment for partial/failed rollouts is crude (discard entire trajectory; uniform discounted terminal reward), which the authors flag as future work. Error recovery remaining weak after RL suggests the framework alone doesn't teach robustness. Results heavily depend on LLM-as-judge verifiers (GPT-5.4, Gemini 2.5 Pro, GPT-4o, o4-mini) whose reliability could inflate scores. Synthetic-task-only training raises questions about distribution match to real benchmarks and potential overfitting to the pipeline's task style. The gap to frontier proprietary models remains large, so 'matching larger models' claims apply mainly in the GUI setting against specific open baselines. Compute/cost details (single 8xB200 node, 32-48h runs) may understate difficulty of the distributed Kubernetes orchestration at larger scale.
