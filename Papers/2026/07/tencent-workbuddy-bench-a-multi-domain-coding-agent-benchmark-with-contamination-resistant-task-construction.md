# Tencent WorkBuddy Bench: A Multi-Domain Coding-Agent Benchmark with Contamination-Resistant Task Construction

## TL;DR
Tencent WorkBuddy Bench is a fully open, multi-domain coding-agent benchmark spanning Code (80 tasks), Web (70), Office (50), and Security (60), where every task is reverse-engineered from real commits/CVEs/business scenarios and rewritten as colloquial, underspecified, role-played requests so prompts aren't web-searchable. It matters because it combines distribution-informed realism with contamination resistance by construction (plus versioning) while still releasing everything—tasks, tests, gold solutions—for full auditability, deliberately refusing a single cross-subset average.

## Abstract
> We introduce Tencent WorkBuddy Bench, a multi-domain evaluation suite for coding agents; this report documents its construction methodology, scoring protocol, and a cross-model leaderboard. At its core is a unified evaluation framework for constructing and running distribution-informed coding-agent tasks across four work domains - Code, Web, Office, and Security. Rather than adapting public issue text, every task is reverse-engineered from a real commit, pull request, or business scenario and rewritten as a short, colloquial, role-played request, so that a task's prompt is not recoverable by web-searching the underlying issue, pull request, or commit thread. Because the dataset is released openly - task directories, environment images, evaluation harness, tests, and reference solutions - contamination resistance rests on this construction together with dataset versioning rather than on secrecy. The four subsets - repository-level engineering, front-end development, office and business workflows, and red-/blue-team security - probe complementary facets of real work, each with its own verification style. All are packaged in a uniform task-directory format and run, under a uniform and reproducible protocol, on two agent harnesses (CodeBuddy Code and Claude Code); the full open release makes the benchmark reproducible end to end and directly auditable, since any third party can re-run each task and inspect its content. Because each subset uses a different scoring instrument, scores are not comparable across subsets and the suite reports no suite-wide average. We report a cross-model leaderboard across several model families.

## Highlights
- Four subsets deliberately use different scoring instruments (Code=hidden tests, Web=rule/LLM-VLM/agent rubric, Office=Rule+evidence-grounded LLM Judge blend, Security=deterministic scoring.py), so no suite-wide average is reported by design.
- No model tops all eight boards: Claude Opus 4.8 leads 5 (Code both harnesses, Web both, Office cbc), GLM-5.2 (open-weight) leads both Security boards (76.32 cbc / 80.86 cc), and GPT-5.5 leads Office cc (86.05).
- Harness choice is not neutral: Security shows an 8.6-point mean absolute shift between CodeBuddy Code and Claude Code, and Code rank order flips (GPT-5.5 vs GLM-5.2); Office moves least (~0.86 median shift).
- Hardest Code categories are bug_fix (mean 0.47) and api_contract (0.47); easiest are feature_pipeline (0.94) and testing (0.88). Only 10 of 80 Code tasks are bug fixes—a deliberate expansion beyond SWE-bench framing.
- Models score higher on Data & Algorithm tasks (~74%) than Coding tasks (~65%); Code scores sit below the same config's Office score, often by 10+ points.
- Spend and rank are decoupled: GPT-5.5 posts top-tier scores on the leanest budgets (6.9k output tokens/run on Code cbc), while DeepSeek-V4-Flash emits ~3.3x more output under cc yet scores 14.74 points lower.
- Security is the heaviest track (30–89 turns/run; MiniMax-M3 hits 88.8 turns and ~11.1M cache-inclusive input tokens); Claude Opus 4.8 refused 13 Security tasks under Claude Code.

## Method
Every task is anchored to a concrete origin—a real commit/PR (Code), a historical CVE (Security whitebox audits), or a business scenario (Web, Office, synthetic Code/Security)—then reverse-engineered and rewritten as a short, colloquial, deliberately underspecified natural-language request (Code voices five requester personas; Security assigns professional roles). The request withholds root cause, reference diff, and target file, forcing the agent to recover context from the workspace. Tasks match internal usage taxonomies (categories, modes, difficulty) without reusing any raw user data. Each task ships as a Harbor-style directory (task.toml, instruction.md, environment/Dockerfile+workspace, tests/test.sh+grading, optional gold.patch) with a strict packaging boundary: the Dockerfile copies only the visible workspace, and grading assets under tests/ stay outside the image and are introduced only after the agent finishes acting. Code tasks pass oracle-gated admission (baseline reward \u22640.3, gold-patch oracle reward =1.0). Execution runs in isolated containers under two harnesses (CodeBuddy Code default, Claude Code alternative), reasoning effort fixed to high, 200k context with common auto-compaction, WebSearch and AskUserQuestion disabled, think mode, averaged over three runs. Scoring formalism: track score is unweighted mean of per-task rewards r_t in [0,1]; Web applies penalty subtraction with fatal-item zeroing; Office blends Rule score (fraction of deterministic checks passing) and Judge score (binary semantic rubrics over fixed post-task evidence) with a per-task weight w_i between 0.70–0.95, macro-averaged; Security combines artifact+correctness+robustness deterministically behind five anti-cheat layers (banned-literal scanning, renamed-input tests, overlay/tamper tests, encoding-dependence tests, low-weight decoys).

## Evals & Results
Seven models evaluated on all four tracks under both harnesses (think mode, 3-run average, 0–100 scale): Claude Opus 4.8, GPT-5.5, GLM-5.2, HY-3 (Hunyuan), MiniMax-M3, DeepSeek-V4-Pro, DeepSeek-V4-Flash. There are no external agent baselines—the leaderboard is cross-model and cross-harness. Leadership splits three ways across the eight boards. Code metric is per-run average hidden-test pass rate (verifiers: pytest-injected 22/80, boolean assertions 54/80, JSON-report 4/80). Web has 786 scored rubric items (62 rule, 676 LLM/VLM, 48 agent-judge). Office uses 50 tasks with dual Rule/Judge channels; cross-model means decline easy/medium/hard (84.6/80.3/73.1 cbc). Security uses deterministic PoC/flag verification, IOC matching, YARA zero-false-positive match rate, and macro-F1/Kendall-tau report scoring. A diagnostic HY-3 rerun with cross-turn reasoning passback gained +3.82 (cbc) and +1.92 (cc) on Code. One cell (Claude Opus 4.8 Code under cc, 77.90) uses a modified do-not-ask instruction and is flagged as not fully comparable.

## So What (for practitioners)
Treat the evaluation harness as a first-class variable: identical models can re-rank across harnesses (especially on Security, ~8.6pt shifts), so report harness/version and reasoning mode explicitly and never assume single-harness rankings transfer. Underspecified, colloquial prompts expose requirement-disambiguation and codebase-grounding failures that clean issue reports hide—dominant failure modes are navigating to the wrong files, looping on test edits, and semantically-correct-but-contract-mismatched output (a single dropped API field zeroes dependent checks). Evaluate final workspace state, not just chat text, to catch 'plausible summary without updating the workbook' failures. Separate deterministic rule checks from LLM-judge semantic rubrics, ground judges in fixed post-task evidence, and never let judge conclusions override deterministic outcomes to bound judge bias. Token/turn spend is a poor proxy for quality—leaner models often match or beat expensive ones. For security-domain automation, budget for far higher turn/token consumption and expect refusals on security-flavored requests. The contamination-by-construction + versioning + full-release pattern is a reproducible template for building auditable internal benchmarks without exposing user data.

## Open Questions / Critiques
Contamination resistance covers only the searchable-prompt path—models may still have seen the underlying public commit code or CVE analysis, and full open release invites future scraping into training data, mitigated only by versioning, not eliminated. Code is heavily Python-dominated (only 4 cross-language ports), so difficulty and gap findings may not generalize. LLM/VLM and agent-judge components (Web, Office) carry unquantified model-judge bias, potentially favoring familiar output styles or same-family models. Serving asymmetry is a real confound: HY-3 is served first-party while all others go through third-party endpoints with uncontrolled parameters, and results are tied to specific harness builds. One leaderboard cell uses a nonstandard instruction, breaking strict comparability. Office is text-first (no OCR/VLM/GUI), so results don't cover visual or desktop-GUI agent work. Because scoring instruments differ across subsets there is deliberately no aggregate, making holistic 'best agent' claims impossible from this suite alone.
